# The Chart or the Summary Sheet: Reproducing MemT-1.0 on a DGX with FlashBlade

Every long conversation with a language model has a storage problem hiding behind the latency problem. The model answers from a working state it built by reading the whole conversation, and if you want to come back tomorrow, somebody has to keep that state or rebuild it. For a 256K-token history on a 35B-parameter model the state is about 5 GB, and rebuilding it takes between 27 seconds and three minutes depending on the serving stack. Multiply by the number of users who expect to pick up where they left off and the question stops being about GPUs.

In October 2026 the MemTensor team published *MemT-1.0: Towards Memory-Native Evolution* (arXiv:2610.26825), a model family that replaces the growing cache with a fixed-size, trained memory. The paper reports that at 128K tokens of history the small model, MemT-1.0-Nano, answers 1.86x faster end to end and needs 66x less persistent storage than the same backbone reading the full history. Those are numbers I want to see on my own hardware before I believe them, and the paper names no hardware at all. So we spent a day on a DGX A100 with a FlashBlade attached, reproduced the efficiency and storage sections, and then measured something the paper does not: what it costs to put each kind of state on shared storage and bring it back.

The storage claim reproduces to the byte. The speed claim reproduces in direction but at roughly two thirds of the paper's magnitude on A100s. And moving session state to and from storage, which the paper never times, is where the 40 MiB memory makes the biggest practical difference. Code, raw results and figures are in the repository linked at the end.

## A one-page summary sheet instead of the whole chart

Here is how I think about it. A doctor who has seen you for ten years has two ways to prepare for your visit. One is to pull your entire chart from the records room and read every page before saying a word. The other is to read the one-page summary sheet clipped to the front, the one they update as each visit goes along. The chart grows with every visit. The summary sheet is always one page and holds whatever the doctor decided was worth writing down.

A transformer reading full context is the doctor with the whole chart. The working state it keeps for a conversation, the **KV cache** (the per-token key and value vectors that every attention layer saves so it can look back at earlier tokens), grows linearly with the history. For Qwen3.6-35B-A3B, the backbone MemT-1.0-Nano is built on, the 10 full-attention layers store 20,480 bytes per token, which is why 256K tokens come to about 5 GB. Building that cache is the **prefill** step, and its cost grows with history length too.

MemT-1.0-Nano is the summary sheet. It adds a trained memory block to each of the backbone's 10 attention layers, 16 heads of a 256 by 256 matrix each, 40 MiB in FP32 for the whole model, and it stays 40 MiB whether the history is 512 tokens or a million. As the model reads a conversation it updates that matrix token by token with a gated delta rule, the same family of update the backbone's 30 linear-attention layers already use. At query time the model reads the memory instead of the history, so the claim is that it is both faster to answer and cheaper to keep.

The summary sheet has an obvious cost that the paper is honest about and we did not test: it is lossy. The paper's quality benchmarks need a GPT-4.1-mini judge and eleven harnesses, and we had neither the API key nor the week. Everything below is about speed and bytes, which is what a storage team can actually measure.

## How we tested it, and the two things we did differently

We followed the paper's protocol from Section 6.5. Histories come from the BEAM benchmark (Tavakoli et al., arXiv:2510.27246), 35 long conversations sliced to 512, 2K, 8K, 32K, 64K, 128K and 256K tokens. Each system first prepares the history, Nano by committing it to memory in 2048-token slices and the full-context baseline by chunked prefill into a KV cache. Then it answers a fixed 512-token query with a forced 128-token reply, five times, with the prepared state restored to the GPU before each query so the restore counts toward time to first token. Both systems ran in Hugging Face transformers in BF16 on two A100-80GB GPUs at batch size 1, as the paper describes, and the full-context baseline is the same model with the memory turned off, so weights and kernels are identical between the two arms.

Two things differ from the paper, and both matter when you read the speed numbers.

First, the memory writer. The checkpoint ships a reference implementation of the memory update that loops over tokens in Python. It is correct and slow, about 2.4 seconds to commit a 2048-token slice against 0.38 seconds for the plain prefill of the same slice. The authors' serving code uses a chunked Triton kernel, but it is noncommercial-licensed and SGLang-only, so we wrote a small Apache-2.0 patch (`bench/memt_fast_writer.py`) that routes the same recurrence through the MIT-licensed `flash-linear-attention` kernel the backbone already depends on. Commit time for a 2048-token slice fell to 0.43 seconds, and the resulting memory matches the reference loop to a relative error of about 2e-3, the TF32 tensor-core precision on A100. In the summary-sheet picture, the reference loop is the doctor writing the sheet one word at a time and putting the pen down after each word; the kernel writes the same sentences a paragraph at a time. The sweep below uses the kernel; with the shipped loop, Nano is slower than full context at every history length on this machine.

Second, the floor under time to first token. On A100, transformers dispatches the backbone's 256 experts per layer through a host-side loop, which puts a floor of about 350 ms under every query regardless of history length. The paper's Nano TTFT is 104 to 112 ms, so the authors were on faster hardware or a different dispatch path. This does not change the shape of the curves, but it compresses the TTFT ratio, so I show the paper's numbers and ours side by side.

## The storage claim reproduces exactly

We serialized each system's state after history preparation to safetensors and measured the bytes. Nano's memory is 41,944,024 bytes on disk at every history length, which is 40.00 MiB of tensor data plus a 1 KiB header. The full-context state is 20,480 bytes per token of attention KV plus a constant 32 MiB for the 30 linear-attention layers' recurrent and convolution state. At 256K tokens that is 4.99 GiB against the paper's 5.06 GiB; the gap is that transformers keeps the recurrent state in BF16 while the paper counts FP32, and with the FP32 bytes added back the fit across all 35 histories is 20,312 bytes per token plus 64.3 MiB, within rounding of the paper's 20 KiB per token plus 62.5 MiB. At 128K tokens the ratio is 64x on our bytes and 65x on the paper's accounting, against the 66x in the abstract.

The chart grows a page per visit, the summary sheet stays one page, and the ratio at a long history is what the paper says it is.

## The speed claim reproduces in direction, not in magnitude

End-to-end time here means preparing the history plus answering one query with a 128-token reply, so it rewards whichever system digests the history fastest. The paper reports parity at 32K, 1.20x at 64K, 1.86x at 128K and 3.99x at 256K in Nano's favor. Our sweep over 35 histories gives full context ahead at 32K (Nano 0.83x), near parity at 64K (0.95x), then Nano ahead by 1.41x at 128K and 2.68x at 256K. The crossover, the history length at which Nano starts winning, is between 64K and 128K on our machine against roughly 32K in the paper.

The reason is visible in the components. At 256K, full-context prefill took 174.7 s and Nano's memory commit took 57.4 s. Nano wins because committing to memory is a linear-time scan while prefill through 10 full-attention layers is not, but on A100 the memory write is not as cheap relative to prefill as it is in the paper. Part of that is our kernel path, which runs the memory update as a separate pass after each slice's forward rather than fused into it, as the authors' path does.

Time to first token is the better test of the architectural claim because it isolates query time. Nano's TTFT is flat at 366 to 370 ms across all seven history lengths. Full context rises from 362 ms at 512 tokens to 767 ms at 128K and 1,253 ms at 256K, a 3.40x gap at 256K against the paper's 4.19x. The shape is the paper's shape, a flat line and a rising one. The flat line sits at 350 ms rather than 105 ms because of the expert-dispatch floor, which is a property of transformers on A100, not of the memory.

## What it costs to file each kind of state, which the paper does not measure

Here is where we left the paper behind, and where the records room enters the story. A serving system that lets users resume conversations has to persist the state somewhere other than GPU memory, and the two states are very different objects to a storage system: one 40 MiB file per session, or one multi-gigabyte file that keeps growing. We measured three things on the FlashBlade with the Linux page cache bypassed, so the numbers are the storage system's and not the client's RAM. The mounts were NFSv3 over RDMA and NFSv4.1 over TCP, both on 200 GbE with `nconnect=16`, with a local NVMe RAID as a reference.

Pulling one state back cold is the first. A 40 MiB MemT snapshot reads in 8.2 ms over RDMA. The 128K full-context state (2.6 GB) reads in 455 ms and the 256K state (5.2 GB) in 849 ms, about 6 GB/s from a single stream. That is the difference between a restore a user cannot perceive and one they can.

Many sessions at once is the second. With 32 processes each pulling a different 5.2 GB state, the RDMA mount sustained 23.7 GB/s aggregate and TCP 18.3 GB/s, against 7 to 8 GB/s for the local NVMe RAID. For the small MemT objects the picture is less tidy, and it held up when we re-ran it on an idle storage path with 1 to 64 concurrent readers. TCP reaches 16 GB/s by 8 concurrent 40 MiB reads and stays there through 64, with a 95th-percentile latency of 89 ms at 32. RDMA matches it up to 16 readers, then drops at 32: 5.2 GB/s for the 40 MiB object and 8.8 GB/s for a 71 MiB one, with 95th percentiles of 263 to 274 ms, and only partly recovers at 64. It is not a hard ceiling, because one 40 MiB repetition at 32 ran at 14 GB/s and the 71 MiB object was back to 16 GB/s at 64, but it is repeatable. We have not root-caused it; it looks like a small-object concurrency effect on the RDMA client path rather than on the array, and for a tier of 40 MiB session objects it is the first number I would check on your own mount.

The loader is the third, and it surprised me most. Reading the 40 MiB file with the standard `safetensors` library took 62.7 ms against 8.2 ms for the raw read. The library does a buffered read, a copy into Python bytes and a parse, and for a 40 MiB object those steps cost 7 to 8 times the I/O itself. For small session objects the loader is where the time goes, not the storage.

Then we closed the loop end to end on both stacks. On the HF side, resuming a MemT session from a cold FlashBlade read, copying it to the GPU and prefilling the query to the first token took 375 ms in total, of which the read was 8 ms and the copy 2.4 ms. The storage system is a rounding error on the query. Restoring the full-context KV cache the same way took 2.25 s at 256K: 0.89 s to read 5 GB, 0.23 s to copy it to the GPUs and 1.1 s of query prefill against a 256K-token cache, so there the storage system is 40 percent of the wait.

On the production side we ran the backbone in vLLM 0.32 with the Pure Storage KV Accelerator connector, which persists the KV cache to FlashBlade in 1056-token chunks and reloads it when a prefix matches. This is the realistic version of the chart in the records room. At 256K tokens the first query recomputes from scratch in 26.9 s, a repeat with the cache still on the GPU answers in 0.64 s, and a restore from FlashBlade with the GPU and host pools emptied answers in 1.54 s. The restored path stores 23.9 KiB per token, a little more than the 20 KiB of raw KV because the hybrid model's recurrent state is checkpointed alongside it, 6.36 GB in 492 files for the 256K session. A 17x saving over recomputation is a good result for the chart, and it is still about 150 times more bytes to keep and move than the summary sheet.

## What this means for a storage tier that holds session state

Both kinds of object are coming, and I would plan for both. A memory-native model gives you a fixed, small object per session, which turns the storage problem from capacity and bandwidth into object count and small-I/O latency. A terabyte holds about 23,800 MemT sessions and 184 full-context sessions at 256K. If your users return to long conversations, the summary sheet is the object you want to be filing, and the thing to engineer for is fast small reads at high concurrency, plus a loader that does not spend 50 ms parsing a 40 MiB file.

The chart is not going away, because the summary sheet is lossy and because most models in production today are not memory-native. For those, a FlashBlade over NFS restores a 5 GB session state in under a second and sustains over 20 GB/s across 32 concurrent restores, so the KV cache does not have to be recomputed, and does not have to live in GPU or host memory, to be fast enough. The two objects want different things from the storage system, and it is worth knowing which one you are building for.

## Keep the chart, start filing the summary sheet

MemT-1.0-Nano's fixed 40 MiB memory is exactly as large as the paper says and 64 to 65 times smaller than the full-context cache at 128K tokens. Its end-to-end speed advantage shows up on A100s, later and smaller than in the paper, and only once you replace the checkpoint's reference memory writer with a kernel. Its flat time to first token is real, with a floor set by the serving framework rather than the memory. On the storage side, which the paper leaves out, a 40 MiB summary sheet comes back from FlashBlade in 8 ms while a 5 GB chart takes 850 ms raw or 1.5 s through a production serving path, both of which beat the 27 to 175 seconds of recomputing it.

One caution. Everything here is efficiency and bytes on a single DGX with a single storage array; we did not measure whether the memory remembers the right things, and the paper's own quality numbers show it trailing retrieval on some benchmarks. The right time to measure the storage side of a memory-native model is now, while you are deciding what your session tier has to hold, not after the models arrive and the records room is already full of charts.
