A language model that keeps notes instead of re-reading the transcript

MemT-1.0 gives a frozen Qwen or DeepSeek model a fixed-size memory it writes into after every turn and reads from on every token. The memory for a whole session is 40 MiB, no matter how long the conversation gets. This page explains what that means, how the model is built, and what we measured when we reproduced the paper's efficiency and storage claims on a DGX A100 with FlashBlade.

What we found · measured 2026-11-10

Three results from the reproduction

1Storage reproduces exactly

The Nano memory file is 41,944,024 bytes, 40.00 MiB, at every history length from 512 to 256K tokens. Full context costs 20,480 bytes per token plus 32 MiB of linear-attention state, 4.99 GiB at 256K against the paper's 5.06 GiB. That is 64× more than Nano at 128K, or 65× if the recurrent state is counted in FP32 the way the paper counts it; the paper says 66×.

2Speed reproduces in direction, at about two thirds of the size

Nano beats full context by 1.41× at 128K and 2.68× at 256K, where the paper reports 1.86× and 3.99×. The crossover sits between 64K and 128K (0.95× at 64K) rather than at 32K. Nano's time to first token is flat, as claimed. This needs a fused memory writer: with the per-token writer the checkpoint ships with, Nano is slower than full context at every length.

3Restoring from storage, which the paper did not measure

A 40 MiB session restores cold from FlashBlade in 8.2 ms, and a resumed Nano session answers in 375 ms at any history length, of which 8 ms is the read. A 256K-token full-context state takes 849 ms to read and 2.25 s to resume in Hugging Face; vLLM with pKVA brings it back in 1.54 s against 26.9 s to recompute. A terabyte holds about 23,800 Nano sessions or 184 at 256K.

In plain words

What MemT does, for people who do not build models

The problem. Today's chat models have no memory of their own. Every time you send a message, the whole conversation so far is sent along with it and the model reads it again. To avoid redoing that work from scratch, serving systems keep a cache of the model's working notes on every token it has read, the KV cache. That cache grows in lockstep with the transcript. For the model behind MemT-1.0-Nano it is about 20 KiB per token, so a 256K-token session carries 5 GiB of cache. Long sessions get slower to answer, more expensive to hold in GPU memory, and awkward to pause and resume, because resuming means either reloading gigabytes or recomputing them.

The idea. Give the model a small, fixed-size memory of its own and teach it to use it. After each turn, the model distills what it just read and wrote into that memory, then forgets the raw text. On every token it generates, it also reads from the memory alongside its normal attention. The memory is not text and not a database. It is a set of matrices inside the network that the model updates with learned rules for what to erase, what to write, and how fast to forget. For the Nano model those matrices total 40 MiB. They are the same size after one turn and after a thousand.

An analogy. A full-context model is a stenographer who re-reads the entire court record before every reply. MemT is a clerk with a notebook of fixed size: after each exchange the clerk updates the notebook, and later answers come from the notes. The notebook is faster to consult and trivial to carry between rooms. It is also lossy. Some details get smudged or overwritten, and the paper is candid that systems which keep the raw text and search it still answer detailed recall questions better.

What it is not

Not retrieval (RAG). Nothing is searched or pasted back into the prompt. Not fine-tuning. The 36B backbone weights never change at inference; only the 40 MiB state does. Not a vector database. The state is a learned associative memory, not a list of records.

What the paper reports

Across 11 memory benchmarks, MemT-1.0-Nano scores 47.0 and Flash 50.6, ahead of other parametric-memory methods (best 38.1) but behind text-based memory systems (up to 68.6). At 128K tokens of history, Nano answers 1.86× faster end to end than full context and keeps 66× less state. General ability is largely preserved.

What we saw first-hand

On our A100s the released model recalled the four facts in the authors' demo and 13 of 18 attributes from a six-person document. On a dense list of 240 unrelated facts it failed exact name lookups that full context got right. The 40 MiB and the 20 KiB-per-token figures matched exactly, and the full sweep later confirmed them at all seven history lengths.

Why a storage team cares. The object you persist per user changes from a KV cache that grows without bound to a 40 MiB file that does not. Every session resume becomes a 40 MiB read. That is a different shape of workload for the storage tier, and it is what the FlashBlade experiments below measured.
Architecture

Where the memory lives inside the network

MemT-1.0-Nano starts from Qwen3.6-35B-A3B as released and freezes it. The backbone is a hybrid: 30 of its 40 layers use Gated DeltaNet, a linear-attention mechanism with a small recurrent state, and 10 use ordinary full attention. A native memory block is bolted onto each of those 10 full-attention layers and nowhere else.

The write rule, one token at a time
Mi = (I − uiTui) · Di · Mi−1 + uiT(ωi ⊙ vi)
  • Di = diag(exp λi) forgets a little, with a separate rate for each of the 256 key channels. Initial half-lives are drawn between 2K and 32K tokens.
  • (I − uᵀu) erases whatever the memory currently associates with this token's key, scaled by the erase gate. The square root on β is the paper's stability fix.
  • uᵀ(ω ⊙ v) writes the new value at that key, scaled by the write gate.
  • Reading is a single matrix product: the query picks out a 256-d value from each head's 256 × 256 matrix.

Pausing and resuming

Full context: save or recompute the cache, 20 KiB per token of history. MemT: save one 40 MiB file. The authors' server exports it as a safetensors snapshot; the HF code does the same, and the two formats are interchangeable.

Writing is not free

A commit runs the turn's tokens through the whole backbone plus the update rule. Nano processes history in 2,048-token slices. The paper's speed advantage comes from doing this once per slice rather than re-attending over all past tokens on every new query.

Many sessions, one model

Weights are shared. Each live session owns a 40 MiB slot on the GPU; the authors' server holds six per rank. Idle sessions can be evicted to storage and brought back by loading their file, which is the pattern we tested on FlashBlade.

Speed

What the authors measured, and what we measured

End-to-end latency is the time to ingest the history and then generate a 128-token reply. The authors ran all three systems with Hugging Face inference on two GPUs they do not name, so absolute numbers do not transfer. We ran the same protocol on 2 × A100-80GB over 35 BEAM histories, 5 repetitions each, and compare ratios and the shape of the curves.

Time to first token

The authors report Nano answering in a steady 104 to 112 ms at every history length, while full context climbs to about 257 ms at 128K and 445 ms at 256K. We see the same shape on a higher floor: Nano flat at 366 to 370 ms, full context 362 ms at 512 tokens, 767 ms at 128K and 1,253 ms at 256K. That is 2.09× and 3.40× against the paper's 2.44× and 4.19×. The ~350 ms floor is Hugging Face's MoE expert dispatch on A100, not the memory.

Where the crossover sits

Paper: slower at short histories, even at 32K, then 1.20× faster at 64K, 1.86× at 128K and 3.99× at 256K. Ours: 0.93× at 512, 0.83× at 32K, 0.95× at 64K, then 1.41× at 128K and 2.68× at 256K, so the crossover falls between 64K and 128K. At 256K full context spends 174.7 s preparing the history against Nano's 57.4 s.

The writer decides the result. The released Hugging Face code writes memory with a per-token Python loop: 2.36 s per 2,047-token slice on an A100. Our kernel writer commits the same slice in 0.43 s. With the shipped writer Nano is slower than full context at every length (310 s of preparation at 256K against 71 s with the kernel writer), so every Nano number on this page uses the kernel writer.

Saving and resuming from FlashBlade

All reads use O_DIRECT so the client page cache cannot help. RDMA is NFSv3 over RDMA, TCP is NFSv4.1, local is the DGX's NVMe RAID.

One session, cold

The 40 MiB Nano file reads in 8.2 ms over RDMA. A full-context state takes 455 ms at 128K and 849 ms at 256K, about 6 GB/s from a single stream. Parsing the same 40 MiB file through the safetensors library costs 62.7 ms, so a raw read into pinned memory is worth doing.

Many sessions at once

32 concurrent 5.2 GB restores pull 23.7 GB/s over RDMA, 18.3 GB/s over TCP and 7 to 8 GB/s from local NVMe. For small objects TCP holds 16 to 17 GB/s from 8 to 64 sessions (p95 89 ms at 32); RDMA dips at 32 sessions (5.2 GB/s for Nano files, p95 263 to 274 ms) and partly recovers at 64.

Capacity and the production path

A terabyte holds about 23,800 Nano sessions or 184 full-context sessions at 256K. vLLM 0.32 with pKVA writes 23.9 KiB per token, 6.36 GB in 492 files per 256K session, and restores it from FlashBlade in 1.54 s against 26.9 s to recompute (0.79 s against 8.68 s at 128K).

Glossary

Terms used on this page

Token
The unit a model reads and writes, about three quarters of an English word. 256K tokens is roughly 190,000 words.
Context window
The most text a model can consider at once. The Nano backbone's is 262,144 tokens; beyond it the oldest text is dropped.
KV cache
Per-token keys and values each attention layer stores so it need not recompute them. For this backbone, 20 KiB per token across its 10 attention layers.
Time to first token (TTFT)
Delay between sending a query and receiving the first word of the reply. It includes reading the prompt and restoring any saved state.
Commit
The moment MemT writes a completed turn, or a 2,048-token slice of a document, into the memory state. The only operation that changes the state.
Memory state, snapshot
The ten 16 × 256 × 256 matrices that hold a session's memory, 40 MiB in FP32. Saved as a safetensors file named by layer.
Gated DeltaNet-2 (GDN-2)
The update rule family MemT uses: a recurrent associative memory with learned erase and write gates and a forgetting rate per key channel. The "stable" variant applies the erase gate under a square root.
Hyper memory, local memory
The authors' names for the trainable projections and gates (hyper, frozen at inference) and the per-session state matrices (local, updated at commit).
Mixture of Experts (MoE)
Each layer has 256 small feed-forward networks and routes every token to 8 of them, so 36B parameters are stored but about 3B run per token.
Mixture-of-Storage (MoS)
The paper's way to grow memory capacity: several memory blocks per layer with a router. Released models use one block per layer.
pKVA
Pure Storage's KV accelerator, a vLLM connector that saves and restores KV cache chunks on FlashBlade so a prefix computed once can be reused later or elsewhere.
BEAM
A benchmark of 35 long synthetic conversations, each over 850K tokens, with questions probing ten memory abilities. The paper used it for the latency sweep; so do we.
